# KODA Market authored-v2 progress revision

The revision manifest (`content/market_revision.json`) is the explicit scope. Its affected IDs include materially changed reused foundation tasks, current Market tasks, and retired old Market tasks. Unrelated tasks keep their identifiers, evidence and drafts. The manifest's revision name is persistent; changing it is a separate migration decision.

Local SQLite applies the revision during normal `init_db()`. It acquires a write transaction, records affected attempts/hints/reviews in `content_revision_archive`, clears only those active rows, rebuilds activity from retained current-catalog attempts and writes `metadata.content_revision:<revision>`. Reapplying the same revision preserves new attempts. No user database was opened or migrated during implementation; the orchestrator owns backup and final application after QA.

Browser storage applies once for each anonymous profile/account before cloud hydration or practice mounting. Old affected states and the affected last-task pointer are archived under `koda:content-revision:<revision>:<profile>:archive`; completed and draft states already stamped with this revision survive. The application marker is separate from the one-time calm notice. Interrupted migration retries preserve the first archive. A storage failure before archival leaves active evidence intact. Unrelated task state, private datasets, theme, account information and achievement storage are not changed.

Cloud storage uses revision-qualified **internal storage keys**: `market-authored-v2::<public-task-id>` for affected tasks. Public catalog IDs, routes and API exercise IDs are unchanged. The existing Supabase schema has a text task key and no task-catalog foreign key, so no new DDL, destructive RPC or remote account reset is needed. Old unqualified rows remain stored as inactive historical evidence. Current-version rows hydrate on a new device without being deleted; old rows cannot override them. Backend attempts and hint operations and frontend draft/import operations share this mapping. Progress and history decode and filter current evidence before metrics or visible history limits. Unknown/retired IDs are excluded using current catalog metadata.

Affected pending cloud timers are cancelled and in-flight responses are guarded; account changes guard all in-flight writes/hydration. A previous deployed client can still write its old unqualified rows, but those rows do not count or hydrate in the new revision. Newly authored API submissions continue through the existing validator. Earned trophy history remains historical recognition and is not revoked.
